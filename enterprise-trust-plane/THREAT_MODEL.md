# Trust product threat model

## Protected assets and trusted parties

Assets: verifier and issuer private keys; approved policies; credential holder
identity; one-time challenge state; revocations; signed decisions; independently
retained checkpoint history; separately provisioned licensing roots.

Trusted inputs: authenticated operator configuration, approved issuer procedures,
pinned verifier/witness/licensor public keys, wall-clock time, unmodified code,
OS process isolation and database transactions. Source documents are not proven
true merely by hashing or signing their claims.

## Enforced controls

| Threat | Control | Evidence |
| --- | --- | --- |
| Altered claims or vendor/holder identity | Issuer signature and strict Passport schema | Credential mutation tests |
| Stolen bearer credential | Holder signs fresh scoped presentation | Wrong-holder, substitution and replay tests |
| Tenant/audience/purpose confusion | Exact scope policy and signed presentation | Scope mutation tests |
| Reuse or concurrent reuse of nonce | SQLite BEGIN IMMEDIATE and one-time consume | Sequential, concurrent and separate-process restart tests |
| Expired or stale source claims | Credential interval and buyer-defined max age | Expiry and freshness tests |
| Revoked issuer, credential or license | Durable operator tombstones | Revocation tests; no key-ID reuse |
| Policy change after challenge | Challenge pins policy digest | Configuration-change regression |
| Signing failure after nonce consume | Event, nonce and receipt outbox share transaction | Injected signer-failure test |
| Malformed/deep/noncanonical JSON | Bounded strict parser, duplicate and surrogate rejection | Negative tests and 200 generated byte-input examples |
| Existing hash-chain corruption | Full local chain check before authorization | Corrupt-history denial test |
| Checkpoint fork or rollback at witness | Persistent monotonic observed-head state | Fork, extension and rollback tests |
| Multiple votes from same signing key | Distinct witness key requirement; verifier cannot self-witness | Quorum manipulation tests |
| License copied across subject/product/capability | Exact signed entitlement and relying-party scope | License-gate tests |
| Self-asserted hardware provenance | No software enrollment promotion; explicitly configured evidence adapter | Missing-adapter and required-hardware denial tests |
| Exposed worker private key file | Owner/mode checks, O_NOFOLLOW, bounded read | Permissions/symlink tests |

## Explicit limitations and production gates

- No production hardware adapter is included. A configured adapter must validate
  real trust chains, device identity, nonce binding, relevant revocation and time
  evidence. The interface does not itself perform those checks. Hardware records
  expire and require revalidation after restart. Worker signing uses a software
  Ed25519 key file; no HSM signing or Secure Enclave integration is claimed.
- The worker is a bounded local process interface. Separate processes sharing a
  host or administrator are not independent remote trust domains. Network TLS,
  client authentication, authorization, rate limits, storage budgets and remote
  root distribution require implementation before exposing it as a service.
- Root/database/configuration administrators can replace code, delete revocation
  records or rewrite/rollback local storage. A hash chain cannot defend against
  a complete coherent rollback. Protect storage and retain signed checkpoints
  with genuinely independent operators; do not label local storage immutable.
- Witnesses observe signed heads; they do not audit all events, establish truth
  of control claims, prove complete history or prevent a malicious verifier from
  issuing a dishonest checkpoint. Different keys are not proof of different
  administrators. The client must obtain and retain a sufficiently recent head
  from trusted independent operators; checking an old unexpired bundle alone
  does not prove it is the latest checkpoint.
- Licensing checks are an application access primitive. There is no settlement,
  royalty routing, usage quota, agreement-law verification or legal compliance
  determination. Older receipt inclusion proofs are absent. A downstream action
  must enforce its own authorization lifetime and idempotency.
- The ledger validates its full chain before authorizing; this trades prototype
  simplicity for growing verification cost. Production scaling needs audited
  snapshots/inclusion proofs, service budgets and measured load/recovery tests.
- Canonicalization is local integer-only JSON, not RFC 8785, and credentials are
  a project-specific format. No W3C VC, accreditation, HIPAA, banking regulation,
  FIPS, ISO or independent security certification is represented by a PASS.
- An issuer may sign false claims. An operator may configure an inappropriate
  rule or trust root. Buyer-approved control semantics and issuer accountability
  are required. Relative-time claims need periodic reissuance or absolute-time
  control definitions; policies should not treat them as permanently current.
- Ed25519 application signatures are not post-quantum. The separate custom native
  hybrid v2 key establishment needs formal independent cryptographic review,
  authenticated peers, key confirmation and a real transport protocol.

The tests establish the specified software behaviors. They do not establish
absence of all defects or security against a compromised root administrator.
